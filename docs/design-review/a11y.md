# Accessibility and Web Performance Review

**Overall verdict: 8/10.** Strong semantic foundations and excellent initial-load performance. The main weaknesses are enlarged-text navigation, mobile focus visibility, and accessibility inside the third-party booking calendar. These need correction before claiming WCAG 2.2 AA conformance.

Reviewed `main` at `0f00d4a` on 12 November 2026: all 25 content pages, the live 404, source code, and all 50 supplied screenshots. Used curl, Chromium, axe, keyboard checks, and Lighthouse. Repository unchanged; [tester summary posted to issue 11](https://github.com/digitalfreedom-co-za/tattoogutachten.de/issues/11#issuecomment-6829188745).

| Mobile Lighthouse measurement | Home | Booking page |
|---|---:|---:|
| Performance | 99 | 100 |
| Accessibility | 100 | 100 |
| LCP | 2.0 s | 1.5 s |
| CLS | 0 | 0 |
| Total Blocking Time | 0 ms | 0 ms |

These are single-run laboratory results for initial navigation. They do not establish field INP or validate the calendar after scrolling.

Verified strengths include descriptive page titles, `lang="de"`, one H1 per content page, orderly heading levels, meaningful image alternatives, landmarks, a working skip link, native FAQ controls, and basic menu keyboard operation. Normal 320 px and 375 px layouts had no horizontal overflow. No-JavaScript navigation and blocked-calendar fallbacks worked. Oxblood on paper passes comfortably at **7.95:1**; graphite on paper achieves **6.92:1**. The preview’s intentional `noindex` is not a defect.

## Findings

### 1. Major: enlarged text pushes navigation outside the viewport

**Component:** Site-wide header; homepage introductory labels  
**Location:** `src/components/layout/Header.astro:20`, `:24`, `:31`; `src/pages/index.astro:50`

**Problem:** With the root text size enlarged to 200% at a 1280 px viewport, every page expanded to approximately **2209 px** wide. The booking button began around x=1851, outside the viewport. Desktop navigation remains active while its non-wrapping contents outgrow the available width. Homepage introductory labels also collide with the image area.

**Why it matters:** People enlarging text lose immediately visible navigation and booking access. This is an enlarged-text resilience issue relevant to WCAG 1.4.4; ordinary narrow-screen reflow passing does not cover it.

**Fix:** Switch to the compact menu when the header’s contents no longer fit, using available component width or measured overflow. Allow the homepage labels to wrap or stack. Verify browser text-only enlargement as well as 200% page zoom. Do not hide overflow to conceal the problem.

### 2. Major: the mobile booking bar covers focused content

**Component:** Fixed mobile CTA  
**Location:** `src/components/layout/StickyCta.astro:30`, `:58`, `:74`; `src/styles/global.css:72`

**Problem:** On `/leistungen/tattoo-gutachten/` at 375 × 812, keyboard navigation placed the focused “Hygiene-Gutachten” link at y≈731–755 while the booking bar began at y≈730. Its title was completely covered. Several FAQ controls were partially covered. This remained after scrolling and animations settled.

**Why it matters:** Keyboard users cannot reliably read the focused destination. The stretched card outline remains partly visible, so that reproduction alone should not be described as an unequivocal wholly-obscured-component failure. It nevertheless demonstrates a substantive focus-visibility defect. WCAG’s minimum obstruction criterion concerns complete component obstruction. [W3C guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum)

**Fix:** Reserve the bar’s actual height in bottom scroll padding and ensure focused controls are scrolled into the unobstructed area. Alternatively, temporarily hide the bar when it overlaps focused content. Body padding at the document end is insufficient.

### 3. Major: the fixed booking button’s focus ring fails contrast

**Component:** Mobile booking CTA  
**Location:** `src/styles/global.css:111`, `:118`; `src/components/layout/StickyCta.astro:15`, `:36`

**Problem:** The settled focus ring uses signal red `#b8211c` against ink `#17140f`, producing **2.86:1** contrast. The existing brass focus override only matches descendants of `.bg-ink`; the sticky bar sets its background through scoped CSS instead.

**Why it matters:** The author-defined focus indicator falls below the 3:1 non-text contrast requirement.

**Fix:** Apply the existing brass-light focus treatment explicitly to `.sticky-cta :focus-visible`, or give the container the shared dark-background class. Brass-light against ink achieves approximately **9.07:1**.

### 4. Major: the booking iframe explicitly disables zoom

**Pages:** Home booking section and `/termin/`  
**Integration location:** `src/scripts/booking.ts:92`  
**Provider-controlled source:** Cal.com embedded document

**Problem:** The loaded iframe contains:

```html
maximum-scale=1, user-scalable=no
```

The parent document correctly allows zoom, but the embedded document requests a zoom restriction. Axe flags this inside the iframe.

**Why it matters:** Calendar interaction is a central task, and users needing magnification must retain that capability. Actual enforcement varies by browser; the restriction should still be removed.

**Fix:** Obtain a provider correction or use an embedding option that preserves zoom. If unavailable, replace the restricted embed with an accessible booking implementation. Parent-page CSS cannot repair a cross-origin document’s viewport metadata. Verify pinch zoom and enlarged booking controls on mobile devices.

### 5. Major: a calendar description link fails text contrast

**Page:** `/termin/`, full calendar  
**Integration location:** `src/config/booking.ts:41`; `src/scripts/booking.ts:97`  
**Provider-controlled element:** Event-description hyperlink

**Problem:** The calendar renders the `tattoogutachten.de` link in blue `#2b7fff` against paper `#f4efe6`. Measured contrast is **3.28:1** at 14 px, below the 4.5:1 requirement. The configured brand palette does not override this rich-text link.

**Why it matters:** Low-vision users can struggle to read the link. Normal-sized link text requires sufficient text contrast. [W3C contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum)

**Fix:** Set rich-text link styling through a supported provider option, using the existing oxblood color. If that styling cannot be controlled, remove the redundant hyperlink from the event description and provide it outside the iframe. Recheck the real event after replacing the demo.

### 6. Minor: parent navigation links incorrectly announce “current page”

**Component:** Desktop and mobile navigation  
**Location:** `src/components/layout/Header.astro:15`, `:30`, `:68`

**Problem:** `startsWith()` marks `/leistungen/` as `aria-current="page"` while viewing an individual service, and `/ratgeber/` while viewing an article.

**Why it matters:** Screen readers announce a different destination as the current page, making location information inaccurate.

**Fix:** Use normalized exact-path matching for `aria-current="page"`. Preserve parent-section highlighting through a separate visual state; use `aria-current="location"` only if deliberately representing the current section.

### 7. Minor: changing to desktop navigation loses keyboard focus

**Component:** Responsive menu  
**Location:** `src/components/layout/Header.astro:244`

**Problem:** Opening the mobile menu and resizing beyond the desktop breakpoint closes it without restoring focus. Chromium moved focus to `body` when the focused mobile link disappeared.

**Why it matters:** Rotation, window resizing, or zoom changes can discard a keyboard user’s position.

**Fix:** Before hiding the panel, detect whether it contains focus. Move focus to the equivalent visible desktop navigation link, or another appropriate visible header control. Leave focus unchanged when it was outside the menu.

### 8. Minor: reveal animations delay visibility of focusable content

**Components:** FAQ items, service rows, article rows, cards  
**Location:** `src/scripts/motion.ts:14`, `:26`; `src/styles/global.css:245`

**Problem:** Interactive elements remain focusable while their reveal ancestors have zero opacity. The observer uses a reduced viewport and stagger delays of `index × 90 ms`, followed by a 900 ms transition. Later FAQ entries can therefore remain invisible or faint after entering view.

**Why it matters:** Fast keyboard navigation can outrun the visual reveal. Initial axe contrast failures on long FAQ groups disappeared with reduced motion, confirming that these were animation-state problems rather than incorrect final colors.

**Fix:** On `focusin`, immediately reveal every relevant ancestor and remove its transition delay. Add a `:focus-within` visibility safeguard. Restrict stagger delays to elements appearing together rather than applying increasing delays throughout a long list.

### 9. Minor: the homepage hero unnecessarily waits for reveal effects

**Pages:** Home; portrait treatment on `/ueber-mich/`  
**Location:** `src/pages/index.astro:55`, `:76`; `src/components/ui/ArtImage.astro:50`; `src/styles/global.css:269`

**Problem:** The homepage H1 starts transparent, and the eagerly loaded, high-priority portrait still receives the default 1300 ms clipping reveal. Image loading priority is correct, but visibility remains dependent on JavaScript and animation.

**Why it matters:** This adds avoidable rendering delay to the most important content, particularly on slower devices. The measured homepage LCP was good; this is a resilience improvement, not evidence of failed Core Web Vitals. Rendering delay is a distinct part of LCP. [LCP documentation](https://web.dev/articles/lcp)

**Fix:** Render above-the-fold headings immediately and pass `reveal={false}` to hero portraits. Keep restrained reveal effects for below-the-fold editorial content.

### 10. Minor: scrolling automatically loads a substantial third-party application

**Pages:** Home and `/termin/`  
**Location:** `src/scripts/booking.ts:118`; `src/components/booking/BookingEmbed.astro:32`

**Problem:** Merely scrolling the booking block into view loads Cal.com. The inspected iframe requested **87 resources with approximately 1.69 MB of encoded resource bodies**, including about **1.30 MB of scripts**.

**Why it matters:** Initial Lighthouse results exclude this below-the-fold cost. Automatic loading adds data transfer and processing during reading, with potential interaction latency on slower phones. Field INP was not measured.

**Fix:** On the homepage, replace automatic mounting with an explicit “Kalender laden” action or link to the dedicated booking page. Keep telephone and email alternatives visible. Measure the dedicated calendar’s loading and interactions under mobile throttling before deciding whether it should also require activation.

### 11. Minor: fingerprinted assets have only a ten-minute cache lifetime

**Component:** Hosting configuration  
**Location:** Deployment infrastructure; asset paths configured through `astro.config.mjs`

**Problem:** Curl confirmed `Cache-Control: max-age=600` for hashed font and stylesheet assets under `/tattoogutachten.de/_astro/`. Lighthouse reported approximately **247 KiB** of potential cache savings. Compression works; sampled assets resolve correctly under the base path.

**Why it matters:** Returning visitors encounter unnecessary revalidation of unchanged assets, including roughly 165 KiB across the three font files.

**Fix:** On hosting or a CDN supporting response-header configuration, serve fingerprinted `/_astro/` assets with a long immutable cache lifetime, while keeping HTML short-lived. GitHub Pages does not expose ordinary per-project custom cache headers, so this requires an infrastructure change rather than an Astro markup adjustment.

## Top 5 quick wins

1. Apply the brass focus ring to the mobile booking CTA.
2. Keep focused content clear of the fixed booking bar.
3. Reveal focused cards and FAQ items immediately.
4. Correct exact-page `aria-current` matching.
5. Remove reveal effects from the homepage H1 and hero portraits.
